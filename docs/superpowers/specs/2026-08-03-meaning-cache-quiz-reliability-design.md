# WordBot 词义级缓存与可靠出题设计

## 目标

把“录入单词后尽力重建题库”升级为可验证的产品能力：每个新录入词义立即进入持久化生成队列，在 18 小时冷却期内生成、检查并修复至少两道不同的合格题；正式测验只读取合格缓存题，并按词义执行冷却、当日排除和掌握规则。

## 已确认的产品规则

1. 最小学习单位是 `用户 + word_id`。数据库中的每一条 `words.id` 表示一个独立词义；同一拼写的不同词义必须是不同 `word_id`。
2. 同一套 10 题或同一天的不同题组可以分别出现 `bank（银行）` 与 `bank（河岸）`。
3. 一个词义录入后立即开始生成缓存，但正式题目必须在录入满 18 小时后才可选择。缺少或无效录入时间时按不可出题处理。
4. 每个词义至少维持两道 `quality_status=ready` 的 primary 缓存题。两题必须有不同题干指纹，不能只调换选项。
5. 某词义当天答对后，当天后续所有正式题组都排除该 `word_id`；同一拼写的其他 `word_id` 不受影响。学习日按 `Asia/Shanghai` 计算。
6. 掌握要求是两个不同学习日的连续正确证据；两个日期不要求是连续自然日。任意一次正式答错只清零该词义此前的连续正确证据，下一次答对重新作为第一个正确学习日。
7. 同一天多次答对同一词义最多贡献一个正确学习日。复习题、测试模式和未正式提交的答案不计入掌握证据。
8. 达到使用阈值或题目被判定过时后，后台补充新变体，始终保持至少两道不过度使用的合格题。

## 方案选择

### 采用：持久任务表 + 词义级 worker + 只读缓存出题

新增 `question_generation_jobs` 表保存每个词义的生成状态、尝试次数、下次执行时间和最后错误。录入事务完成后 upsert 一条任务；进程内 worker 负责认领到期任务，针对单个 `word_id` 生成、校验和修复题目。服务重启后未完成任务仍可继续。

选择该方案的原因：它把缓存生成从不可靠的 fire-and-forget Promise 变成可恢复状态机；任务粒度与产品粒度一致；诊断可以直接回答每个词义为何没有两道合格题。

### 未采用：继续全用户 fire-and-forget 重建

改动较小，但请求返回后任务可能丢失，多次录入会并发删除/覆盖缓存，也无法证明某个新词义已经生成两题。

### 未采用：测试开始时实时生成

会把模型延迟和失败暴露给孩子，违背 18 小时预生成缓存的核心要求，只保留为管理员修复工具，不作为正式测验降级路径。

## 组件与边界

### `question-generation-job.js`

定义任务状态和纯状态转换：`pending -> generating -> validating -> repairing -> ready`，异常进入带 `next_attempt_at` 的 `retry_wait`；超过自动修复上限进入 `needs_manual_review`。任何状态都不得让未通过质量检查的题进入正式题池。

### `question-generation-service.js`

只处理一个 `word_id`：读取词义快照，生成候选题，调用统一质量检查，按拒绝原因定向重试，原子写入两道不同的 ready 题，并把旧题标记 stale/retired。它不负责学习顺序和 18 小时冷却。

### `question-generation-worker.js`

周期认领持久任务。任务认领必须有 lease，避免多个 Render 实例重复处理；过期 lease 可以恢复。每轮处理数量有上限，避免生成任务阻塞 API。

### `quiz-word-queue.js` 与 `quiz-adapter.js`

正式测验先按 `word_id` 构造资格队列，再从该 `word_id` 的 active ready 缓存中选题。选择条件同时满足：录入满 18 小时、当天未答对、尚未掌握、缓存题可用。禁止按标准化英文拼写做当日排除。

### `mastery-service.js`

成为唯一掌握判定入口。按时间顺序处理正式提交记录：错误清零；正确且学习日不同则推进；达到两个未被错误打断的不同学习日后掌握。

### 诊断与前端

缓存状态 API 返回用户级汇总和词义级失败原因，包括任务状态、ready 数量、拒绝原因、尝试次数和最后错误。前端开始按钮根据结构化状态显示“开始测试”“题库准备中”“当前可测试 N 题”或“题库生成失败”，不再用遮挡按钮的固定 toast 表示准备状态。

## 数据库迁移

新增 `question_generation_jobs`，包含 `user_id`、`word_id`、`status`、`attempt_count`、`next_attempt_at`、`lease_owner`、`lease_expires_at`、`last_error_code`、`last_error_detail` 和时间戳；`word_id` 唯一并外键关联 `words`。为 `(status, next_attempt_at)` 和 `user_id` 建索引。

表启用 RLS，不向 `anon` 或 `authenticated` 授权，只显式授予 `service_role` 服务端所需权限。根据 Supabase 2026-04 的 Data API 变更，新表不假设自动暴露；迁移同时包含 service-role grant，并在部署前验证 PostgREST 可访问性。

`question_cache` 增加或校验 `variant_slot`、`cache_state`、`available_from`、`question_fingerprint` 和拒绝诊断字段。迁移必须幂等，不删除现有 ready 缓存；旧数据通过后台回填任务逐词义补齐。

## 质量门槛

一题只有同时满足以下条件才可标记 ready：四个非空且不重复的选项；答案唯一且对应 A-D；目标词只在合理语境中出现；题干明确指向目标词义；干扰项词性和难度合理；中文释义完整；无答案格式泄漏；与该词义另一道 ready 题的题干指纹不同。

自动修复按原因执行，单轮有限重试；失败状态持久化后退避重试。系统不为凑够 10 题降低质量门槛或绕过冷却期。

## 发布验收

1. 调用真实录入接口后可以查到该 `word_id` 的持久任务。
2. worker 完成后该词义至少有两道不同指纹的 ready primary 题。
3. 17:59:59 不可出题，18:00:00 可进入候选。
4. 同一天答对一个词义后只排除该 `word_id`；相同拼写的另一 `word_id` 仍可出题。
5. 周一对、周四对可掌握；周一对、周二错、周三对时周三仅为第一次正确。
6. 服务重启后 pending/retry_wait 任务能够继续。
7. 题目生成失败时状态 API 返回具体拒绝原因，前端不显示无限“0/10 准备中”。
8. 后端、前端和端到端测试全绿后才能推送；部署后用测试账号执行只读状态检查和正式出题冒烟。
